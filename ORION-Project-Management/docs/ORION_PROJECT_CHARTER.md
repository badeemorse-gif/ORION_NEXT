# ORION — ميثاق المشروع

الإصدار: 1.0
الحالة: تأسيسي
المشروع: ORION
المستودع البرمجي: binansScanner
مستودع إدارة المشروع: ORION-Project-Management


==================================================
1. تعريف المشروع
==================================================

ORION هو نظام برمجي لتحليل بيانات السوق وبناء صورة منظمة عن حالة السوق، ثم معالجة هذه البيانات عبر مجموعة من المكونات والمحركات للوصول إلى نتائج وتحليلات وقرارات قابلة للتتبع، مع إمكانية عرض النتائج وتخزينها وإنتاج التقارير.

المشروع مصمم ليكون نظامًا قابلًا للتوسع، وليس مجرد Script منفصل.


==================================================
2. الهدف الرئيسي
==================================================

الهدف الرئيسي من ORION هو بناء نظام منظم وقابل للصيانة والتوسع يقوم بتوفير دورة معالجة واضحة تبدأ من الحصول على بيانات السوق وتنتهي بنتائج وتحليلات وقرارات وتقارير يمكن مراجعتها وتتبع مصدرها.


==================================================
3. الرؤية النهائية
==================================================

الرؤية النهائية هي الوصول إلى نظام ORION مستقر ومنظم يستطيع:

1. الحصول على بيانات السوق من المصادر المعتمدة.
2. تحويل البيانات إلى نماذج داخلية موحدة.
3. تخزين البيانات عند الحاجة.
4. التحقق من صحة البيانات.
5. معالجة البيانات عبر Pipeline واضحة.
6. حساب المؤشرات.
7. تحليل حالة السوق.
8. بناء Profile للسوق.
9. احتساب Scores.
10. إنتاج Decisions.
11. تنفيذ العمليات المسموح بها ضمن حدود النظام.
12. إنتاج تقارير منظمة.
13. تشغيل العمليات بصورة دورية عند الحاجة.
14. توفير API.
15. توفير GUI.
16. توفير اختبارات كافية لضمان الاستقرار.
17. الحفاظ على قابلية التوسع والصيانة.


==================================================
4. طبيعة المشروع
==================================================

ORION ليس ملفًا واحدًا ولا Script بسيطًا.

هو نظام متعدد الطبقات والمكونات.

ويجب التعامل معه على هذا الأساس أثناء التطوير.

أي قرار يؤدي إلى إعادة المشروع إلى بنية Script مركزية أو خلط المسؤوليات بين الطبقات يجب اعتباره تغييرًا معماريًا ويحتاج إلى مراجعة.

7. مبدأ فصل المسؤوليات
==================================================

كل طبقة يجب أن تمتلك مسؤولية واضحة.

المبدأ العام:

Provider
مسؤول عن التعامل مع المصادر الخارجية.

Mapper
مسؤول عن تحويل البيانات الخارجية إلى الصيغ الداخلية المناسبة.

Model
يمثل البيانات داخل النظام.

Repository
ينظم الوصول إلى البيانات.

Storage
ينفذ التخزين والاسترجاع.

Validation
يتحقق من صحة البيانات والنتائج.

Pipeline
ينظم تسلسل مراحل المعالجة.

Engines
تنفذ عمليات التحليل والمعالجة المتخصصة.

Decision
مسؤول عن بناء القرار وفق المدخلات المعتمدة.

Execution
مسؤول عن العمليات التنفيذية التي يعتمدها النظام.

Report
مسؤول عن إخراج النتائج.

API
توفر واجهة وصول خارجية.

GUI
توفر واجهة المستخدم.

Scheduler
ينظم التشغيل الدوري.

Bootstrap
يبني ويربط مكونات النظام.

Application
يدير دورة تشغيل التطبيق.


==================================================
8. مصادر البيانات
==================================================

المصدر الحالي الرئيسي لبيانات السوق هو Binance.

يجب عزل Binance عن المنطق الداخلي للنظام.

الهدف من ذلك هو عدم جعل بقية النظام تعتمد على تفاصيل API الخاصة بمزود واحد.


==================================================
9. البيانات الحساسة
==================================================

لا يتم تخزين:

- API Keys.
- API Secrets.
- Passwords.
- Tokens.
- Private Keys.

داخل ملفات المصدر أو Git.

تستخدم إعدادات البيئة أو آلية آمنة مناسبة لتوفير بيانات الاعتماد.

المشروع يجب أن يظل قابلًا للمشاركة والمراجعة دون كشف الأسرار.


==================================================
10. الاختبارات
==================================================

الاختبارات جزء أساسي من المشروع.

لا تعتبر الاختبارات مرحلة لاحقة يتم إضافتها بعد اكتمال كل الكود.

يتم تطوير الاختبارات بالتوازي مع تثبيت المكونات المهمة.

الهدف هو الوصول إلى:

- Unit Tests.
- Integration Tests.
- Pipeline Tests.
- Regression Tests.
- Operational Tests.

13. فريق العمل
==================================================

فريق العمل يتكون من ثلاثة أطراف:

--------------------------------------------------
1. GPT
--------------------------------------------------

قائد الفريق وصاحب القرار الفني الوحيد في المشروع.

مسؤولياته:

- قيادة المشروع.
- تحديد سير العمل.
- مراجعة المعمارية.
- مراجعة الملفات.
- تحديد التعديلات المطلوبة.
- إصدار تعليمات التعديل.
- مراجعة التعديلات.
- اعتماد الملفات.
- اعتماد القرارات.
- مراجعة التفاصيل.
- تحديد الانتقال بين المراحل.
- الحفاظ على توافق التنفيذ مع الهدف النهائي.

--------------------------------------------------
2. Gemini
--------------------------------------------------

مهندس تنفيذ الأكواد.

مسؤوليته:

تنفيذ الأكواد أو التعديلات التي يتم تحديدها من GPT.

لا يعتبر Gemini صاحب القرار المعماري النهائي.

--------------------------------------------------
3. مالك المشروع / المنفذ
--------------------------------------------------

مسؤول عن:

- تنفيذ التعليمات عمليًا.
- التعامل مع البيئة المحلية.
- نقل الأكواد والتعديلات.
- حفظ الملفات.
- تشغيل الأوامر.
- تنفيذ الاختبارات المطلوبة.
- تنفيذ أوامر Git.
- نقل النتائج إلى الفريق للمراجعة.

لا يتم تغيير القرار الفني من طرف التنفيذ المحلي دون الرجوع إلى GPT.


==================================================
14. قاعدة السلطة الفنية
==================================================

GPT هو صاحب القرار الفني النهائي.

عند وجود اختلاف بين:

- اقتراح Gemini.
- رغبة التنفيذ المحلي.
- قرار سابق.
- تصميم محتمل.

يجب الرجوع إلى GPT لاتخاذ القرار.

الهدف ليس تقليل دور أي طرف، بل منع تضارب القرارات.


==================================================
15. أسلوب تعديل الملفات
==================================================

عند الحاجة إلى تعديل ملف:

1. تتم مراجعة الملف كاملًا عند الحاجة.
2. يتم تقييم تأثير التعديل على الملفات المرتبطة.
3. يتم تحديد التعديل المطلوب.
4. يتم تنفيذ التعديل.
5. يتم مراجعة الملف بعد التعديل.
6. يتم تشغيل الاختبارات المناسبة.
7. يتم اعتماد التعديل.
8. يتم تحديث الوثائق عند الحاجة.


==================================================
16. قاعدة التعديل الجزئي
==================================================

عندما يكون المطلوب تعديل جزء محدد من ملف:

يجب الحفاظ على بقية الملف دون تغيير غير مقصود.

لا يتم إعادة كتابة الملف بالكامل بطريقة تؤدي إلى تغييرات جانبية غير مطلوبة.

الهدف هو أن يكون كل تغيير:

- محددًا.
- مفهومًا.
- قابلًا للمراجعة.
- قابلًا للتتبع.


==================================================
17. قاعدة تأثير الملفات المرتبطة

==================================================
23. ما يعتبر نجاحًا
==================================================

لا يعتبر ORION ناجحًا لمجرد أن:

- البرنامج يبدأ التشغيل.
- API تعمل.
- GUI تفتح.
- البيانات تصل.

النجاح النهائي يعني أن النظام:

- يعمل بصورة صحيحة.
- معماريته مستقرة.
- مكوناته مترابطة بصورة صحيحة.
- نتائجه قابلة للتتبع.
- اختباراته مناسبة.
- أخطاؤه معروفة ومدارة.
- وثائقه محدثة.
- أسراره محمية.
- قابل للصيانة والتوسع.


==================================================
24. حدود المشروع
==================================================

أي وظيفة جديدة يجب تقييمها مقابل الهدف الأساسي للمشروع.

لا تتم إضافة وظيفة لمجرد إمكانية تنفيذها.

إذا كانت الوظيفة تغير طبيعة النظام أو تضيف مسؤولية كبيرة، يجب اتخاذ قرار معماري قبل تنفيذها.

26. الحالة الحالية
==================================================

ORION في مرحلة تثبيت خط الأساس وتثبيت وثائق إدارة المشروع.

تم إنشاء أول Commit رسمي.

ويجري حاليًا تثبيت الوثائق المرجعية قبل بدء المراجعة المعمارية التفصيلية.

==================================================

هذه الوثيقة هي المرجع الأساسي لهوية المشروع وهدفه وحدوده وأدوار فريق العمل.

مسودة تأسيسية حتى اعتماد مجموعة وثائق إدارة المشروع بالكامل.
