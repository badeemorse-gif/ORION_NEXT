==================================================
1. الغرض
==================================================

هذا الملف هو السجل الرسمي للمشاكل المعروفة في مشروع ORION.

يتم استخدامه لتسجيل:

- الأخطاء البرمجية.
- المشاكل المعمارية.
- مشاكل الاعتماديات.
- مشاكل الاختبارات.
- مشاكل التشغيل.
- مشاكل التكامل.
- مشاكل الأداء عند إثباتها.
- مشاكل الأمان عند اكتشافها.
- أي سلوك غير متوافق مع التصميم المعتمد.
- أي تعارض بين الكود والوثائق.
- أي تعارض بين وثائق المشروع.


==================================================
2. الهدف
==================================================

الهدف من هذا السجل هو منع:

- نسيان المشاكل المكتشفة.
- إعادة التحقيق في نفس المشكلة دون معرفة تاريخها.
- اعتبار المشكلة المعروفة مشكلة جديدة.
- إغلاق مشكلة دون توثيق سبب إغلاقها.
- تجاهل مشكلة لأنها ظهرت في وثيقة أو مسار غير متوقع.


==================================================
3. قاعدة أساسية
==================================================

لا يتم تسجيل شيء كمشكلة مؤكدة اعتمادًا على التخمين.

يجب التمييز بين:

- مشكلة مؤكدة.
- اشتباه يحتاج إلى تحقيق.
- تحسين مقترح.
- قرار معماري.

إذا كان الأمر قرارًا معماريًا، يتم تسجيله أيضًا في:

ORION_DECISIONS.md


==================================================
4. حالات المشاكل
==================================================

OPEN

المشكلة مؤكدة ولم تتم معالجتها.

INVESTIGATING

يتم التحقيق في سبب المشكلة.

FIXED

تم تنفيذ إصلاح للمشكلة.

VERIFIED

تم اختبار الإصلاح والتأكد من نجاحه.

CLOSED

تم إغلاق المشكلة رسميًا.

WONTFIX

تم اتخاذ قرار بعدم إصلاحها، مع توثيق السبب.

DUPLICATE

المشكلة مكررة لمشكلة أخرى.


==================================================
5. مستويات الأولوية
==================================================

CRITICAL

تمنع تشغيل النظام أو تسبب خطرًا كبيرًا على البيانات
أو الأمان.

HIGH

تؤثر بصورة كبيرة على وظيفة أساسية.

MEDIUM

تؤثر على وظيفة أو مكون ولكن النظام يستطيع الاستمرار.

LOW

مشكلة محدودة التأثير.

12. العلاقة مع القرارات المعمارية
==================================================

إذا كشفت المشكلة عن خلل في التصميم أو الحاجة إلى
تغيير معماري:

1. تسجل المشكلة هنا.
2. يتم تحليلها.
3. يتم اتخاذ القرار المعماري.
4. يسجل القرار في ORION_DECISIONS.md.
5. يتم تنفيذ القرار.
6. يتم تحديث المشكلة.
7. يتم تحديث CHANGELOG عند الحاجة.

==================================================

- الكود تغير.
- الخطأ لم يظهر مرة واحدة.
- البرنامج بدأ التشغيل.

يجب التحقق من الإصلاح وفق طبيعة المشكلة.

الحالة المفضلة:

FIXED
↓
VERIFIED
↓
CLOSED


==================================================
14. المشاكل المتعلقة بالملفات
==================================================

إذا كانت المشكلة مرتبطة بملف معين، يجب ذكر:

- اسم الملف.
- الجذر.
- المسار الكامل.
- المكون.
- الطبقة.
- سبب المشكلة.
- الملفات المتأثرة.
- الاعتماديات المتأثرة.

ولا يتم إصلاح الملف بصورة معزولة إذا كان التعديل يؤثر
على ملفات أخرى.


==================================================
15. المشاكل المتعلقة بالاعتماديات
==================================================

إذا اكتشفت مشكلة في Dependency:

يجب فحص:

- مصدر الاعتماد.
- المستهلك.
- دورة الاعتماد.
- Dependency Container.
- Bootstrap.
- الاختبارات المتأثرة.
- الملفات المرتبطة.

ولا يتم إزالة الاعتماد أو تغييره دون تقييم تأثيره.


==================================================
16. المشاكل المتعلقة بالاختبارات
==================================================

إذا فشل اختبار:

لا يتم تعديل الاختبار لمجرد جعله ينجح.

يجب أولًا تحديد:

هل المشكلة في:

- الكود؟
- الاختبار؟
- العقد المعماري؟
- البيانات؟
- البيئة؟
- الاعتماديات؟

ثم اتخاذ القرار المناسب.


==================================================
17. المشاكل الأمنية
==================================================

أي مشكلة تتعلق بـ:

- API Key.
- API Secret.
- Password.
- Token.
- Private Key.
- بيانات اعتماد.
- تسريب معلومات حساسة.

تعتبر مشكلة أمنية ويجب التعامل معها بأولوية مناسبة.

لا يتم تسجيل الأسرار نفسها داخل هذا الملف.


==================================================
18. مشاكل الوثائق
==================================================

إذا ظهرت معلومة مهمة في وثيقة غير الوثيقة المتوقعة:

لا يتم تجاهلها.

يجب:

1. التحقق من المعلومة.
2. تحديد الوثيقة المناسبة.
3. اعتماد المعلومة إذا كانت صحيحة.
4. تحديث الوثيقة المناسبة.
5. تحديث الوثائق المرتبطة عند الحاجة.
6. تسجيل المشكلة هنا إذا كان وجود المعلومة في المكان
   الخاطئ قد يسبب تضاربًا أو خطأ في التنفيذ.

الوثائق كلها جزء من حالة ORION ويجب عدم التعامل معها
كأن كل وثيقة مستقلة عن الأخرى.


==================================================
19. تعارض الكود والوثائق
==================================================

عند وجود تعارض بين:

- الكود.
- الوثائق.
- القرارات.
- الاختبارات.
- حالة Git.
- حالة GitHub.

لا يتم التخمين.

يجب فحص الحالة الفعلية أولًا.

ثم:

1. تحديد الحقيقة الحالية.
2. تحديد الوثيقة أو الكود غير المتوافق.
3. تسجيل المشكلة عند الحاجة.
4. تصحيح المصدر غير المتوافق.
5. تحديث الوثائق المرتبطة.
6. تسجيل التغيير.
