# ORION — بروتوكول العمل الرسمي للمشروع

الإصدار: 2.2
الحالة: ACTIVE
المشروع: ORION

==================================================
1. وظيفة الوثيقة
==================================================

هذه الوثيقة تحدد **كيف ننفذ العمل** داخل ORION.

لا تعيد تعريف هدف المشروع أو المعمارية أو المرحلة الحالية.
مصادر هذه المعلومات محددة في ORION_CONTROL_INDEX.md.

==================================================
2. المبدأ الأعلى
==================================================

ORION مشروع تنفيذي وليس مشروع توثيق فقط.

الوثائق وسيلة لضبط التنفيذ وليست سببًا لتوقفه.

المسار الافتراضي:

EVIDENCE
↓
DECISION
↓
IMPLEMENTATION
↓
TARGETED TEST
↓
FULL VERIFICATION
↓
DOCUMENTATION
↓
NEXT STEP

لا يتحول العمل إلى:

DOCUMENT
↓
DOCUMENT
↓
WAIT

==================================================
3. دور GPT والمستخدم
==================================================

GPT يقود التحليل الفني والمراجعة المعمارية وتحديد الخطوة التنفيذية التالية عندما تكون الأدلة كافية.

المستخدم هو صاحب القرار النهائي في:

- تغيير هدف المشروع.
- تغيير النطاق.
- القرارات الاستراتيجية.
- المفاضلات البشرية.
- المخاطر غير القابلة للعكس التي تحتاج اعتمادًا.

أما القرار الفني الواضح المدعوم بالكود والاختبارات والمعمارية فهو مسؤولية GPT ضمن نطاق المشروع.

==================================================
4. الدليل أولًا
==================================================

لا يعتمد قرار مهم على الذاكرة وحدها.

مصادر الدليل:

1. الكود الحالي.
2. الاختبارات الفعلية.
3. Git/GitHub.
4. القرارات المعتمدة.
5. المعمارية الحالية.
6. PROJECT STATE.
7. الوثائق المرتبطة.

إذا تعارضت وثيقة قديمة مع الواقع الحالي:

1. إثبات التعارض.
2. تحديد الحقيقة الحالية.
3. تحديد المصدر غير المتوافق.
4. تحديث الوثيقة المالكة.
5. تسجيل القرار عند الحاجة.
6. متابعة التنفيذ.

لا يتم التراجع عن تنفيذ صحيح فقط لإرضاء وثيقة قديمة.

==================================================
5. المراجعة المتناسبة
==================================================

حجم المراجعة يتناسب مع حجم القرار.

تعديل صغير:
→ الملف + الاعتماديات المباشرة + الاختبارات.

تعديل مكون:
→ المكون + المستهلكون + الاختبارات.

تعديل معماري:
→ Architecture + Decisions + Findings + Roadmap + المكونات المتأثرة.

تعارض جوهري أو مراجعة شاملة:
→ مراجعة موسعة للوثائق والكود والاختبارات ذات الصلة.

لا تتم مراجعة المشروع كله بلا سبب، ولا يتم اتخاذ قرار معماري كبير بعد قراءة ملف واحد فقط.

==================================================
6. Vertical Slice
==================================================

لا يتم اعتبار المكون مكتملًا بمجرد إنشاء Class أو ملف.

يجب إكمال Vertical Slice:

Contract
↓
Implementation
↓
Integration
↓
Tests
↓
Downstream Compatibility
↓
Verification

وهذا يمنع تراكم مكونات تبدو مكتملة بينما لا تعمل ضمن المسار الحقيقي.

==================================================
7. Contract First
==================================================

عند إنشاء أو إعادة بناء مكون:

1. تحديد Input Contract.
2. تحديد Result/Output Contract.
3. تحديد المسؤولية والحدود.
4. تثبيت الاختبارات التعاقدية المناسبة.
5. تنفيذ المكون.
6. اختبار التكامل.
7. التحقق من المستهلكين downstream.

لا يتم بناء منطق داخلي كبير قبل تثبيت الحدود عندما تكون الحدود هي جوهر المشكلة.

==================================================
8. أقل تغيير لازم
==================================================

عند وجود منطق مثبت بالاختبارات:

- لا يعاد كتابته دون سبب معماري مثبت.
- لا يتم تغيير عقده لمجرد تحسين شكلي.
- لا يتم توسيع نطاق المهمة بلا حاجة.

عند وجود نقص حقيقي، يعالج بأقل تغيير يحافظ على المسار الصحيح.

==================================================
9. عدم تلويث Domain State
==================================================

MarketDataset يمثل بيانات السوق فقط.

لا يستخدم كمخزن دائم لـ:

Profile
Score
Decision
Execution
Report

المسار الصحيح:

MarketDataset
↓
Engine
↓
Canonical Result

كل مرحلة تملك Result Contract مستقلًا.

==================================================
10. ترتيب العمل الحالي
==================================================

يحدد PROJECT STATE المرحلة الحالية.

في Phase 2 يكون العمل على Core Intelligence فوق الأساس المثبت في Phase 1، ولا تعاد العقود المستقرة إلا عند ظهور ضرورة معمارية مثبتة.

بعد اكتمال Phase 2، ينتقل المشروع إلى Scalping Opportunity Engine وفق ROADMAP.

لا يفرض Future Roadmap تنفيذ GUI أو Explosion Radar أو Trading Bot قبل موعدها.

==================================================
11. الاختبار
==================================================

كل تعديل يحتاج مستوى اختبار مناسبًا لطبيعته.

LEVEL 1
→ الاختبارات الضيقة للمكون المتأثر.

LEVEL 2
→ Full Suite عند اكتمال التعديل أو عند وجود أثر تكاملي.

التعديل المعماري أو العقدي لا يعتمد على اختبار ضيق فقط.

يجب التفريق بين:

FAIL
ERROR
WARNING
DEPRECATION WARNING

التحذير لا يصبح blocker تلقائيًا؛ يصبح blocker إذا أثر على الصحة أو التوافق أو الاستقرار أو النتيجة أو كان سيصبح كسرًا مؤكدًا في المستقبل القريب.

==================================================
12. معالجة الفشل
==================================================

عند ظهور Failure لا يتم تغيير التصميم فورًا.

يتم تحديد السبب أولًا:

- الكود.
- الاختبار.
- العقد.
- التكامل.
- البيانات.
- البيئة.
- الاعتماديات.

ثم يعالج السبب الحقيقي ويعاد الاختبار.

لا يتم تعديل الاختبار لمجرد تحويل الفشل إلى نجاح إلا إذا ثبت أن الاختبار نفسه غير صحيح وفق العقد المعتمد.

==================================================
13. Findings
==================================================

Finding جديدة لا تعني إيقاف التطوير تلقائيًا.

تسجل في ORION_ARCHITECTURE_FINDINGS.md.

إذا أصبحت Blocking أو كان استمرار التطوير يرسخها، تتوقف الخطوة المتأثرة حتى اتخاذ القرار أو الإصلاح.

إذا تم تنفيذها بنجاح:

VERIFIED / CLOSED

ولا تحذف من التاريخ.

==================================================
14. انتقال المراحل
==================================================

لا تنتقل المرحلة لمجرد أن الاختبارات نجحت.

بوابة الانتقال تعتمد على:

Implementation
+
Tests
+
Review
+
Fixes
+
Verification
+
Findings Review
+
Documentation
+
Approval

وPROJECT STATE هو المرجع النهائي للمرحلة الحالية.

==================================================
15. الوثائق
==================================================

عند تغيير معلومة مملوكة لوثيقة:

1. تحديث الوثيقة المالكة.
2. إزالة التكرار من الوثائق غير المالكة إذا وجد.
3. تحديث Decision/Changelog/Findings عند الحاجة.

لا تنشأ وثيقة جديدة إذا كانت وثيقة قائمة تؤدي نفس الوظيفة.
