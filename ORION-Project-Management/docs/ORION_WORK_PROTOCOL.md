# ORION — بروتوكول العمل الرسمي للمشروع

الإصدار: 2.3
الحالة: ACTIVE
المشروع: ORION

==================================================
1. وظيفة الوثيقة
==================================================

هذه الوثيقة تحدد كيف ننفذ العمل داخل ORION.

لا تعيد تعريف هدف المشروع أو المعمارية أو المرحلة الحالية.
مصادر هذه المعلومات محددة في ORION_CONTROL_INDEX.md.

==================================================
2. المبدأ الأعلى
==================================================

ORION مشروع تنفيذي وليس مشروع توثيق فقط.

الوثائق وسيلة لضبط التنفيذ وليست سببًا لتوقفه.

نموذج التطوير الحالي بالحزم:

ARCHITECTURE BOUNDARY
↓
COMPLETE VERTICAL / FUNCTIONAL SLICE
↓
CONTRACTS
↓
IMPLEMENTATION
↓
INTEGRATION COMPATIBILITY REVIEW
↓
DOCUMENTATION
↓
COMMIT
↓
FINAL REPORT

لا يتحول العمل إلى:

DOCUMENT
↓
DOCUMENT
↓
WAIT

==================================================
3. دور GPT والمستخدم
==================================================

GPT يقود التحليل الفني والمراجعة المعمارية وتحديد الخطوة التنفيذية التالية عندما تكون الأدلة كافية.

المستخدم هو صاحب القرار النهائي في:

- تغيير هدف المشروع.
- تغيير النطاق.
- القرارات الاستراتيجية.
- المفاضلات البشرية.
- المخاطر غير القابلة للعكس التي تحتاج اعتمادًا.

أما القرار الفني الواضح المدعوم بالأدلة فهو مسؤولية GPT ضمن نطاق المشروع.

==================================================
4. الدليل أولًا
==================================================

لا يعتمد قرار مهم على الذاكرة وحدها.

مصادر الدليل:

1. الكود الحالي.
2. الاختبارات الفعلية عند توفرها.
3. Git/GitHub.
4. القرارات المعتمدة.
5. المعمارية الحالية.
6. PROJECT STATE.
7. الوثائق المرتبطة.

إذا تعارضت وثيقة قديمة مع الواقع الحالي:

1. إثبات التعارض.
2. تحديد الحقيقة الحالية.
3. تحديد المصدر غير المتوافق.
4. تحديث الوثيقة المالكة.
5. تسجيل القرار عند الحاجة.
6. متابعة التنفيذ.

لا يتم التراجع عن تنفيذ صحيح فقط لإرضاء وثيقة قديمة.

==================================================
5. المراجعة المتناسبة
==================================================

حجم المراجعة يتناسب مع حجم القرار.

تعديل صغير:
→ الملف + الاعتماديات المباشرة + الاختبارات عند الحاجة.

تعديل مكون:
→ المكون + المستهلكون + الاختبارات والعقود المتأثرة.

تعديل معماري:
→ Architecture + Decisions + Findings + Roadmap + المكونات المتأثرة.

تعارض جوهري أو مراجعة شاملة:
→ مراجعة موسعة للوثائق والكود والاختبارات ذات الصلة.

لا تتم مراجعة المشروع كله بلا سبب، ولا يتم اتخاذ قرار معماري كبير بعد قراءة ملف واحد فقط.

==================================================
6. Vertical Slice
==================================================

لا يتم اعتبار المكون مكتملًا بمجرد إنشاء Class أو ملف.

يجب إكمال Vertical Slice بما يكفي ليكون صالحًا للتكامل:

Contract
↓
Implementation
↓
Downstream Compatibility
↓
Documentation
↓
Commit

يمكن تأجيل Full Verification المحلي إلى Integration Gate عندما لا تكون بيئة التشغيل المحلية متاحة للمطور.

==================================================
7. Contract First
==================================================

عند إنشاء أو إعادة بناء مكون:

1. تحديد Input Contract.
2. تحديد Result/Output Contract.
3. تحديد المسؤولية والحدود.
4. تثبيت الاختبارات التعاقدية المناسبة عند الحاجة.
5. تنفيذ المكون.
6. مراجعة التوافق downstream.
7. دمجه فقط عند عبور بوابة التكامل المعتمدة.

لا يتم بناء منطق داخلي كبير قبل تثبيت الحدود عندما تكون الحدود هي جوهر المشكلة.

==================================================
8. أقل تغيير لازم
==================================================

عند وجود منطق مثبت:

- لا يعاد كتابته دون سبب معماري مثبت.
- لا يتم تغيير عقده لمجرد تحسين شكلي.
- لا يتم توسيع نطاق المهمة بلا حاجة.

عند وجود نقص حقيقي، يعالج بأقل تغيير يحافظ على المسار الصحيح.

==================================================
10. ترتيب العمل الحالي
==================================================

يحدد PROJECT STATE المرحلة الحالية.

في Phase 2 يكون العمل على Core Intelligence فوق الأساس المثبت في Phase 1، ولا تعاد العقود المستقرة إلا عند ظهور ضرورة معمارية مثبتة.

بعد اكتمال Phase 2، ينتقل المشروع إلى Scalping Opportunity Engine وفق ROADMAP.

لا يفرض Future Roadmap تنفيذ GUI أو Explosion Radar أو Trading Bot قبل موعدها.

==================================================
11. الاختبار
==================================================

كل تعديل يحتاج مستوى تحقق مناسبًا لطبيعته، لكن الاختبار المحلي ليس شرطًا أن يحدث بعد كل تعديل صغير داخل محادثة المطور.

LEVEL 1
→ Contract/unit tests تُكتب مع الحزمة عند الحاجة.

LEVEL 2
→ CI أو verification مستهدف عندما يكون التنفيذ متاحًا.

LEVEL 3
→ Full Suite / E2E عند Integration Gate أو بوابة الانتقال.

المطور الذي لا يملك بيئة التشغيل المحلية لا يدعي تنفيذ اختبار محلي.

يجب التفريق بين:

FAIL
ERROR
WARNING
DEPRECATION WARNING

التحذير لا يصبح blocker تلقائيًا؛ يصبح blocker إذا أثر على الصحة أو التوافق أو الاستقرار أو النتيجة أو كان سيصبح كسرًا مؤكدًا في المستقبل القريب.

==================================================
12. معالجة الفشل
==================================================

عند ظهور Failure لا يتم تغيير التصميم فورًا.

يتم تحديد السبب أولًا:

- الكود.
- الاختبار.
- العقد.
- التكامل.
- البيانات.
- البيئة.
- الاعتماديات.

ثم يعالج السبب الحقيقي ويعاد التحقق عندما تتوفر بيئة التشغيل المناسبة.

لا يتم تعديل الاختبار لمجرد تحويل الفشل إلى نجاح إلا إذا ثبت أن الاختبار نفسه غير صحيح وفق العقد المعتمد.

==================================================
13. Findings
==================================================

Finding جديدة لا تعني إيقاف التطوير تلقائيًا.

تسجل في ORION_ARCHITECTURE_FINDINGS.md.

إذا أصبحت Blocking أو كان استمرار التطوير يرسخها، تتوقف الخطوة المتأثرة حتى اتخاذ القرار أو الإصلاح.

إذا تم تنفيذها بنجاح:

VERIFIED / CLOSED

ولا تحذف من التاريخ.

==================================================
14. انتقال المراحل
==================================================

لا تنتقل المرحلة لمجرد أن الاختبارات نجحت.

بوابة الانتقال تعتمد على:

Implementation
+
Tests / Verification evidence as available
+
Review
+
Fixes
+
Findings Review
+
Documentation
+
Approval

وPROJECT STATE هو المرجع النهائي للمرحلة الحالية.

==================================================
15. الوثائق
==================================================

عند تغيير معلومة مملوكة لوثيقة:

1. تحديث الوثيقة المالكة.
2. إزالة التكرار من الوثائق غير المالكة إذا وجد.
3. تحديث Decision/Changelog/Findings عند الحاجة.

لا تنشأ وثيقة جديدة إذا كانت وثيقة قائمة تؤدي نفس الوظيفة.

==================================================
16. Git والتطوير والمزامنة
==================================================

GITHUB هو مصدر الحقيقة أثناء التطوير.

المطورون داخل ChatGPT يعملون على فروع GitHub ويكملون حزمًا كاملة داخل نطاقاتهم، ولا يعتمد سير التطوير على GITHUB → LOCAL بعد كل تعديل صغير.

لا يستخدم:

tools\orion_sync.bat

كمسار تشغيلي يومي لمزامنة كل تعديل إلى LOCAL.

وأي أداة آلية قديمة تعتمد على ذلك التعامل تعتبر LEGACY/FROZEN حتى يقرر قائد المشروع خلاف ذلك.

بيئة:

C:\Users\badee\Desktop\ORION_NEXT

هي Development / Integration Working Tree، وليست Sandbox لمزامنة كل فرع.

==================================================
17. Final Materialization
==================================================

عند اكتمال الحزم المطلوبة وقرار التكامل:

GITHUB COMMITS / INTEGRATED STATE
↓
CLEAN FINAL MATERIALIZATION
↓
LOCAL ORION_NEXT
↓
FULL VERIFICATION / E2E / PARITY

يجب أن تعتمد المزامنة النهائية على branch/commit محدد ونسخة نظيفة.

لا تكتب العملية النهائية فوق Working Tree غير مقصود دون بوابة واضحة.

MAIN/ALL mirrors تبقى معزولة عن Development Working Tree.

==================================================
18. تسليم الحزم للمطورين
==================================================

عند تكليف مطور بحزمة واضحة ومحددة:

- ينفذ الحزمة كاملة حتى Definition of Done.
- لا يرسل تحديثًا بعد كل ملف.
- لا يسأل هل يكمل ما دام داخل نطاق المهمة.
- يعالج المشاكل الداخلية ضمن نطاقه.
- يتوقف فقط عند Architectural Blocker حقيقي أو تعارض مع Contract أعلى.
- عند اكتمال الحزمة يرسل تقريرًا نهائيًا واحدًا.

هذا الأسلوب يمنع فقدان سياق التنفيذ ويقلل التشتت.

19. تسليم الملفات
==================================================

عند طلب تعديل ملف برمجي، النسخة المرجعية للتطبيق هي الملف الكامل بعد التعديل، وليس جزءًا مبتورًا منه.
