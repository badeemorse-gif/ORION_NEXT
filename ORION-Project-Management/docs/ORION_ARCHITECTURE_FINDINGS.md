# ORION — ARCHITECTURE FINDINGS

الإصدار: 1.2
الحالة: ACTIVE
المشروع: ORION
المستودع الرسمي: badeemorse-gif/ORION_NEXT

==================================================
1. الغرض
==================================================

هذا الملف هو السجل الرسمي للملاحظات والـFindings الناتجة عن المراجعة المعمارية المستمرة أثناء تطوير ORION.

الغرض منه منع ضياع أي ملاحظة مهمة أثناء استمرار المطور في التنفيذ، مع عدم تحويل كل Finding إلى أمر إيقاف فوري.

هذا الملف لا يغيّر Workflow التطوير الحالي، ولا يعني أن المطور يجب أن يتوقف عند كل Finding.

==================================================
2. قاعدة التعامل مع Findings
==================================================

وجود Finding مفتوح لا يعني إيقاف التطوير.

يستمر التطوير بصورة طبيعية ما دام لا يرسخ التعارض أو يعتمد على قرار غير محسوم.

يتم إيقاف المسار فقط عندما يثبت أن الاستمرار سيؤدي إلى:

- كسر Contract معتمد.
- تثبيت تعارض معماري.
- تكرار مسؤولية في طبقة غير مالكة لها.
- بناء مرحلة لاحقة على قرار غير محسوم.
- الإضرار بالتصور النهائي للمشروع.

==================================================
3. الحالات
==================================================

OPEN

ملاحظة أو تعارض مؤكد ولم تتم معالجته.

INVESTIGATING

تحتاج الملاحظة إلى فحص إضافي قبل اعتمادها كمشكلة.

NEEDS_DECISION

الملاحظة صحيحة أو مؤثرة، لكن تحتاج قرارًا معماريًا قبل التنفيذ.

DEFERRED

تم تأجيلها عمدًا لأن المرحلة الحالية لا تتطلب حلها، مع بقائها مفتوحة للمراجعة.

READY_FOR_FIX

تم حسم المطلوب وأصبحت جاهزة للتنفيذ.

FIXED

تم تنفيذ الإصلاح.

VERIFIED

تم اختبار الإصلاح والتحقق منه.

CLOSED

تم إغلاق الـFinding رسميًا.

==================================================
4. قاعدة عدم ضياع الملاحظة
==================================================

أي Finding يتم اكتشافه أثناء مراجعة ORION يجب أن يبقى مسجلًا حتى يتم:

- حله والتحقق منه، أو
- اتخاذ قرار بتأجيله، أو
- اتخاذ قرار بعدم إصلاحه مع توثيق السبب.

لا تعتبر الملاحظة منتهية بسبب مرور الوقت أو انتقال التطوير إلى طبقة أخرى.

## AF-001 — ترتيب Validation وStorage

تاريخ الاكتشاف:
2026-08-08

الحالة:
VERIFIED / CLOSED

تاريخ التحقق:
2026-08-11

الأولوية:
HIGH

المجال:
Architecture / Data Flow

### الوصف

كان المسار التنفيذي يخزن MarketDataset قبل تنفيذ Validation.

تم تعديل المسار الحالي ليصبح:

Provider
↓
MarketDataset
↓
VALIDATION
↓
STORE valid dataset

### دليل التنفيذ والتحقق

تم إنشاء اختبار عقد صريح في:

binansScanner/tests/test_orchestrator_validation_order.py

ويثبت الاختبار أن:

1. Dataset غير صالح يتم رفضه قبل Storage.
2. storage.execute لا يتم استدعاؤه عند فشل Validation.
3. Dataset صالح يصل إلى Storage بعد نجاح Validation.
4. المسار يصل إلى FINISHED عند نجاح الدورة.

### قرار المراجعة

تم اعتبار Finding محلولة ومتحققة، ولذلك تم نقلها إلى:

VERIFIED / CLOSED

ولا يجب التعامل معها في المراجعات القادمة كـFinding مفتوحة، إلا إذا ظهر Regression جديد.

## AF-002 — تحديد الدور النهائي لـ ProfileResult

تاريخ الاكتشاف:
2026-08-08

الحالة:
NEEDS_DECISION

الأولوية:
MEDIUM

المجال:
Intelligence Contracts

### الوصف

يتم إنتاج ProfileResult بصورة مستقلة، بينما Score الحالي يعتمد على AnalysisResult، وDecision يعتمد على AnalysisResult وScoreResult.

### الملاحظة

يجب حسم ما إذا كان ProfileResult:

1. مخرجًا تحليليًا مستقلًا للاستهلاك اللاحق، أو
2. مدخلًا رسميًا في Score/Decision.

### قاعدة العمل الحالية

لا يتم تعديل Score أو Decision اعتمادًا على هذه الملاحظة بالحدس.

يتم تسجيلها حتى يتم اتخاذ القرار المعماري المناسب وفق هدف ORION النهائي.

## AF-003 — مسؤولية بناء ExecutionPlan داخل Orchestrator

تاريخ الاكتشاف:
2026-08-08

الحالة:
OPEN

الأولوية:
HIGH

المجال:
Architecture / Execution Boundary

### الوصف

يقوم Orchestrator حاليًا ببناء ExecutionPlan وتحويل DecisionResult إلى BUY/SELL/HOLD مع تحديد بعض قيم خطة التنفيذ.

### الملاحظة

هذا يجعل Orchestrator يحمل جزءًا من Business/Execution Mapping Logic بدل أن يقتصر على التنسيق.

### السلوك المستهدف

يبقى Orchestrator مسؤولًا عن التنسيق، بينما يتم وضع منطق تحويل DecisionResult إلى ExecutionPlan في مكون/Contract مسؤول عن هذا التحويل وفق الـTarget Architecture.

### قاعدة العمل الحالية

لا تتم إعادة بناء Orchestrator أثناء استمرار المطور إلا إذا أصبح هذا التداخل خطرًا على التطوير الحالي.

## AF-005 — انجراف وثيقة Project State عن التنفيذ الفعلي

تاريخ الاكتشاف:
2026-08-10

الحالة:
OPEN

الأولوية:
HIGH

المجال:
Project Governance / Documentation Consistency

### الوصف

أثناء المراجعة الحالية ظهر أن ORION_PROJECT_STATE.md ما زالت تصف المشروع بأنه في Architecture Inventory / Target Structure Discovery، وتذكر أن "لا توجد تعديلات برمجية معتمدة في هذه النقطة"، بينما الكود الحالي في main يحتوي بالفعل على تنفيذات وتغييرات معمارية أحدث، ومنها ترتيب Validation قبل Storage.

### الخطر

إذا بقيت Project State متأخرة عن الواقع، فقد تبدأ مراجعة لاحقة من نقطة قديمة، أو يعتقد المطور/المراجع أن إصلاحات أو قرارات لم تحدث بعد بينما هي موجودة فعليًا.

### قاعدة العمل

لا يعني هذا إيقاف المطور.

يجب عند أقرب نقطة توثيق مناسبة تحديث Project State لتصف الواقع الفعلي فقط، مع عدم إعلان أي Phase مكتملة قبل تحقق شروط الإكمال الرسمية.

### Verification المطلوب

مقارنة Project State مع:

- آخر commit على main.
- Architecture Findings.
- Baseline المعتمد.
- آخر التعديلات البرمجية الفعلية.

ثم تحديث الحالة دون اختراع مرحلة جديدة أو اعتبار التطوير مكتملًا قبل أوانه.

## AF-006 — ضرورة منع بقاء ExecutionPlan Mapping كاعتماد ضمني قبل مرحلة Trading Bot

تاريخ الاكتشاف:
2026-08-10

الحالة:
OPEN

الأولوية:
HIGH

المجال:
Future Execution Architecture

### الوصف

Orchestrator الحالي يحتوي على _build_execution_plan() ويحوّل DecisionResult إلى ExecutionSide ويحدد السعر والكمية والثقة والسبب.

هذا مقبول كحل مرحلي طالما لم يتم تثبيته كالعقد النهائي للتداول الحقيقي.

### الخطر المستقبلي

عند الاقتراب من بناء Trading Bot الحقيقي، قد يصبح هذا المنطق مرتبطًا بالـOrchestrator بحيث يصعب فصل:

Decision

عن:

Execution Planning

عن:

Broker/Exchange Execution

وهذا قد يسبب تداخلًا في المسؤوليات أو يجعل اختبار الـDecision مستقلًا عن التنفيذ أصعب.

### قاعدة العمل

لا يتم تعديل هذا الآن لمجرد التنبيه.

لكن قبل اعتماد Trading Bot النهائي يجب حسم ملكية ExecutionPlan mapping رسميًا، واختباره كعقد مستقل إذا أثبتت المراجعة أنه أصبح جزءًا من مسار التداول الدائم.

## AF-007 — عدم الخلط بين Result Contract و Stage Completion

تاريخ الاكتشاف:
2026-08-10

الحالة:
OPEN

الأولوية:
MEDIUM

المجال:
Core Runtime / Verification

### الوصف

وجود Result Contract أو نجاح تنفيذ دالة لا يعني تلقائيًا أن المرحلة المعمارية اكتملت.

مثال ذلك أن Orchestrator ينتج ProfileResult وExecutionPlan، لكن اكتمال المرحلة يتطلب أيضًا التأكد من:

- صحة العقد.
- صحة الـwiring.
- تكامل المستهلكين.
- الاختبارات.
- عدم وجود تعارض مع Baseline.

### قاعدة العمل

لا يتم تحويل مرحلة إلى COMPLETE اعتمادًا على وجود الملف أو class فقط.

يجب تطبيق شروط الإكمال الرسمية للمشروع: Implementation + Tests + Verification + Review + عدم وجود Blocking Issue + تحديث Baseline عند الحاجة.

==================================================
6. قاعدة المراجعة المستمرة
==================================================

في كل مراجعة لاحقة:

1. يتم فحص الـFindings المفتوحة.
2. يتم مقارنة التطوير الجديد معها.
3. يتم تحديد ما إذا كانت ما زالت صحيحة.
4. إذا تم حلها، تنتقل إلى FIXED ثم VERIFIED ثم CLOSED بعد الاختبار.
5. إذا أصبح التطوير الحالي يعتمد عليها، يتم إيقاف المسار وإصدار توجيه تصحيحي للمطور.
6. إذا لم تؤثر على المسار الحالي، يستمر المطور دون تعطيل.
7. يتم أيضًا فحص توافق Project State والـBaseline والـFindings مع التنفيذ الفعلي حتى لا تتكون ذاكرة توثيقية قديمة.

8. قاعدة عدم التضارب
==================================================
