# ORION — EVIDENCE-DRIVEN EXECUTION METHOD

الإصدار: 1.0
الحالة: ACTIVE
المشروع: ORION
المستودع: badeemorse-gif/ORION_NEXT
الفرع: main

==================================================
1. الغرض
==================================================

هذه الوثيقة تحدد منهج التنفيذ العملي لمشروع ORION.

هدفها منع:

- التوقف غير الضروري.
- إعادة التحقيق في نقاط تم حسمها.
- الدوران بين الوثائق دون تنفيذ.
- اعتبار الوثائق القديمة حقيقة مطلقة.
- انتظار قرارات المستخدم في القرارات التقنية الواضحة.
- تنفيذ تعديلات منفصلة دون اختبار تكاملي.
- الانتقال بين المراحل دون دليل.

هذه الوثيقة لا تستبدل وثائق المشروع الأخرى.

وظيفتها تحديد:

"كيف ننفذ"

بينما تحدد الوثائق الأخرى:

- الحالة.
- المعمارية.
- القرارات.
- التاريخ.
- المشاكل.
- خارطة الطريق.

==================================================
2. المبدأ الأعلى
==================================================

ORION مشروع تنفيذي وليس مشروع توثيق فقط.

الوثائق وسيلة لضبط المشروع وليست غاية توقف التنفيذ.

القاعدة الأساسية:

EVIDENCE
↓
DECISION
↓
IMPLEMENTATION
↓
TEST
↓
VALIDATION
↓
DOCUMENTATION
↓
NEXT STEP

ولا يكون التسلسل:

DOCUMENT
↓
DOCUMENT
↓
DOCUMENT
↓
WAIT

==================================================
3. دور GPT
==================================================

GPT هو المسؤول عن قيادة المسار التنفيذي داخل المحادثة.

عند توفر الأدلة الكافية:

- يحدد المشكلة.
- يحدد القرار الفني.
- يحدد الملفات المتأثرة.
- يحدد الاختبارات المطلوبة.
- يحدد الخطوة التالية.
- يحدد ما إذا كان التعديل يحتاج تطبيقًا محليًا.
- يراجع نتيجة التنفيذ.
- يحدد الخطوة التالية دون انتظار توجيه إضافي إذا كانت واضحة.

لا يتم تحميل المستخدم مسؤولية اختيار القرارات التقنية التي يمكن حسمها بالأدلة.

المستخدم هو صاحب القرار النهائي في:

- القرارات البشرية.
- القرارات الاستراتيجية.
- تغيير هدف المشروع.
- تغيير النطاق.
- المفاضلات التي لا يمكن حسمها تقنيًا.

أما القرارات التنفيذية الفنية الواضحة فهي مسؤولية GPT.

==================================================
4. قاعدة عدم التوقف
==================================================

لا يتوقف التنفيذ لمجرد وجود أكثر من خيار تقني.

إذا كان أحد الخيارات:

- أكثر اتساقًا مع المعمارية.
- أقل تغييرًا.
- مدعومًا بالاختبارات.
- لا يكسر العقود الحالية.
- يقرب المشروع من Target Architecture.
- وقابلًا للعكس أو محدود المخاطر.

فيتم اختياره والتنفيذ عليه.

يتم سؤال المستخدم فقط عندما:

1. يكون القرار خارج النطاق الفني.
2. يتطلب تغيير هدف المشروع.
3. يتطلب تغييرًا جوهريًا غير محسوم.
4. توجد مفاضلة حقيقية لا يمكن حسمها بالأدلة.
5. توجد مخاطرة غير قابلة للعكس ويجب اعتمادها.
6. يتطلب القرار حذف بيانات أو مكونات بصورة لا يمكن التراجع عنها.

==================================================
5. قاعدة الدليل أولًا
==================================================

لا يتم اتخاذ قرار معماري أو تنفيذي مهم من الذاكرة وحدها.

مصادر الدليل العملية هي:

1. الكود الفعلي.
2. الاختبارات الفعلية.
3. Git history والحالة الفعلية للمستودع.
4. القرارات المعتمدة.
5. المعمارية المستهدفة.
6. حالة المشروع.
7. بقية الوثائق.

عند وجود تعارض بين وثيقة قديمة وبين:

CURRENT CODE
+
CURRENT TESTS
+
ACCEPTED CHANGES

لا يتم تنفيذ الوثيقة القديمة بشكل أعمى.

يتم:

1. إثبات التعارض.
2. تحديد الحالة الفعلية.
3. تحديد ما إذا كان التغيير الحالي مقصودًا أو غير موثق.
4. تحديث الوثيقة المالكة.
5. تسجيل القرار عند الحاجة.
6. متابعة التنفيذ.

==================================================
6. الواقع الحالي أعلى من الحالة التاريخية
==================================================

قد تحتوي وثائق المشروع على حالة تاريخية لم تعد تعكس آخر تنفيذ.

وجود هذه الحالة لا يعني الرجوع إلى الماضي.

عندما تكون:

CURRENT CODE
+
TEST EVIDENCE

أحدث من:

PROJECT STATE

فهذا يعني أن PROJECT STATE متأخر عن التنفيذ.

لا يتم التراجع عن تنفيذ صحيح فقط لجعل الحالة القديمة متوافقة.

المسار الصحيح:

CURRENT REALITY
↓
VALIDATION
↓
UPDATE PROJECT STATE

==================================================
7. الوثيقة لا توقف التنفيذ
==================================================

وجود قاعدة في وثيقة لا يعني أن GPT يجب أن يتوقف إذا كانت القاعدة:

- قديمة.
- مكررة.
- متعارضة مع الواقع الحالي.
- أو أصبحت غير مناسبة بسبب قرار أحدث.

في هذه الحالة:

1. يتم تحديد التعارض.
2. يتم استخدام المصدر الأعلى سلطة.
3. يتم استخدام الأدلة الحالية.
4. يتم اتخاذ القرار الصحيح.
5. يتم تحديث الوثيقة المالكة.

الهدف هو الحفاظ على حوكمة المشروع دون تحويل الحوكمة إلى blocker.

==================================================
8. قاعدة المراجعة المتناسبة
==================================================

يجب أن يكون حجم المراجعة متناسبًا مع حجم القرار.

قرار صغير:
→ مراجعة صغيرة.

تعديل مكون:
→ مراجعة المكون + الاعتماديات + الاختبارات.

تعديل معماري:
→ مراجعة المعمارية + القرارات + خارطة الطريق + المكونات المتأثرة.

تعارض جوهري:
→ مراجعة موسعة.

لا تتم مراجعة المشروع كله لمجرد وجود تعديل محدود.

وفي المقابل لا يتم اتخاذ قرار معماري كبير بعد قراءة ملف واحد فقط.

==================================================
9. قاعدة Vertical Slice
==================================================

لا يتم تنفيذ المشروع كمجموعة تغييرات متناثرة.

يتم العمل على Vertical Slice واحدة في كل مرة.

مثال:

Profile

تشمل:

- Contract.
- Result.
- Engine.
- Integration.
- Tests.
- Downstream compatibility.

ولا يتم اعتبار المكون منتهيًا بمجرد إنشاء ملف أو Class.

التركيز يكون على:

COMPLETE VERIFIED SLICE

10. ترتيب التنفيذ الافتراضي
==================================================

الترتيب الافتراضي:

Indicator
↓
Analysis
↓
Profile
↓
Score
↓
Decision
↓
Execution
↓
Report
↓
Orchestrator

هذا ترتيب افتراضي وليس قانونًا جامدًا.

يمكن تغييره عندما تثبت الاعتماديات أو المعمارية أن ترتيبًا آخر أكثر صحة.

==================================================
11. قاعدة Contract First
==================================================

عند إنشاء مكون جديد أو إعادة بناء مكون:

1. تحديد Result Contract.
2. تحديد Input Contract.
3. تحديد Output Contract.
4. تحديد حدود المسؤولية.
5. كتابة أو تعديل الاختبارات التعاقدية.
6. تنفيذ Engine.
7. اختبار التكامل.
8. الانتقال للمكون التالي.

لا يتم بناء منطق داخلي كبير قبل تثبيت الحدود العامة للمكون عندما تكون الحدود هي جوهر المشكلة.

==================================================
12. قاعدة عدم تلويث Domain State
==================================================

MarketDataset يمثل بيانات السوق فقط.

لا يتم استخدامه كمخزن للحالة الناتجة من:

- Indicator
- Analysis
- Profile
- Score
- Decision
- Execution
- Report

كل مرحلة تنتج Result Contract مستقلًا.

المسار الصحيح:

MarketDataset
↓
Engine
↓
Canonical Result

وليس:

MarketDataset
↓
إضافة state جديد
↓
Engine
↓
Engine آخر يقرأ state مخفيًا

==================================================
13. قاعدة الاختبار
==================================================

كل تعديل يمر على مستويين:

LEVEL 1
اختبارات المكون المتأثر.

LEVEL 2
الاختبار الكامل للمشروع.

القاعدة:

FAIL
↓
تحليل السبب
↓
إصلاح السبب
↓
إعادة الاختبار

يجب التفريق بين:

- FAIL.
- ERROR.
- WARNING.
- DEPRECATION WARNING.

التحذير لا يتحول إلى blocker إلا إذا أصبح مؤثرًا في:

- الصحة.
- التوافق.
- الاستقرار.
- أو صحة النتيجة.

==================================================
14. قاعدة معالجة الفشل
==================================================

عند ظهور Failure:

لا يتم تغيير التصميم فورًا.

يتم أولًا تحديد:

1. هل الفشل في الكود؟
2. هل الفشل في الاختبار؟
3. هل العقد تغير؟
4. هل الاختبار قديم؟
5. هل المشكلة في البيئة؟
6. هل المشكلة تكاملية؟

ثم يتم إصلاح السبب الحقيقي.

لا يتم إخفاء الفشل بتعديل الاختبار فقط.

ولا يتم تغيير المعمارية لإرضاء اختبار غير صحيح.

==================================================
15. قاعدة Evidence
==================================================

كل نتيجة ناجحة تعتبر Evidence.

مثال:

63 tests
OK

تعني أن مجموعة العقود التي تغطيها هذه الاختبارات تم إثباتها.

لكنها لا تعني تلقائيًا أن المشروع كله مكتمل.

يتم تحديث حالة المشروع بناءً على:

- ما تم إثباته.
- ما لم يتم إثباته.
- ما هو قيد التنفيذ.
- ما هو التالي.

==================================================
16. قاعدة عدم إعادة العمل
==================================================

إذا تم إثبات نقطة باختبار ناجح أو فحص موثق:

لا يعاد التحقيق فيها في كل رسالة.

يعاد فتحها فقط إذا:

- تغير الكود المرتبط بها.
- تغير العقد.
- ظهر Failure جديد.
- ظهر تعارض معماري.
- ظهرت أدلة أقوى.
- تغيرت متطلبات المشروع.

==================================================
17. قاعدة التعامل مع حالة المشروع
==================================================

ORION_PROJECT_STATE.md تمثل أفضل حالة موثقة للمشروع.

لكنها ليست بديلًا عن التحقق من الواقع عند وجود Evidence أحدث.

إذا أثبت التنفيذ الحالي تقدمًا يتجاوز الحالة الموثقة:

لا يتم تجاهل التقدم.

بل يتم:

1. إثباته.
2. تحديد آخر Milestone موثق بالأدلة.
3. تحديث PROJECT_STATE في مرحلة التوثيق المناسبة.
4. تحديد الخطوة التالية من الحالة الجديدة.

==================================================
18. قاعدة التوثيق
==================================================

التوثيق يجب أن يتبع التنفيذ وليس أن يخنقه.

بعد إثبات Milestone:

يتم تحديث:

PROJECT STATE

وعند الحاجة:

CHANGELOG
DECISIONS
KNOWN PROBLEMS
ARCHITECTURE

ولا يتم كتابة صفحات طويلة قبل امتلاك دليل تنفيذي يستحق التوثيق.

==================================================
19. قاعدة القرارات المعمارية
==================================================

إذا اكتشف التنفيذ أن قرارًا سابقًا أصبح غير مناسب:

لا يتم الالتزام به لمجرد أنه قديم.

يتم:

1. إثبات السبب.
2. تحديد البديل.
3. تقييم الأثر.
4. اعتماد القرار الجديد.
5. تحديث الوثيقة المالكة.
6. متابعة التنفيذ.

القرار الصحيح الحالي أعلى قيمة من الحفاظ الشكلي على قرار تاريخي أصبح غير صحيح.

==================================================
20. قاعدة التعديل المحدود
==================================================

لا يتم تعديل ملفات غير مرتبطة بالمشكلة الحالية.

كل تعديل يجب أن يجيب عن:

- لماذا هذا الملف؟
- لماذا هذا التغيير؟
- ما العقد الذي يحميه؟
- ما الاختبار الذي يثبته؟
- ما التأثير downstream؟

إذا كان التعديل أكبر من المشكلة التي يحلها:

يتم تقليص نطاقه.

==================================================
21. قاعدة عدم القفز المعماري
==================================================

لا يتم القفز إلى إعادة هيكلة شاملة لمجرد اكتشاف مشكلة محلية.

القاعدة:

LOCAL PROBLEM
↓
LOCAL EVIDENCE
↓
LOCAL FIX

إلا إذا أثبتت الأدلة أن المشكلة ناتجة عن خلل معماري أوسع.

==================================================
22. قاعدة التقدم المتحقق
==================================================

السرعة المطلوبة في ORION ليست:

FASTEST CODE

بل:

FASTEST VERIFIED PROGRESS

أي:

أسرع تقدم يمكن إثبات صحته.

ويُفضل:

تغيير صغير
+
اختبار سريع
+
نتيجة واضحة

على:

تغيير كبير
+
تحليل طويل
+
نتيجة غير مؤكدة

==================================================
23. قاعدة القرار التنفيذي
==================================================

عندما تكون الخطوة التالية واضحة فنيًا:

GPT يقررها.

لا ينتظر:

"ماذا نفعل الآن؟"

ولا يطلب من المستخدم اختيار:

A / B / C

إذا كان أحدها واضح الأفضلية بالأدلة.

يقدم GPT القرار وسببه، ثم ينتقل إلى التنفيذ المطلوب.

==================================================
24. قاعدة المسؤولية
==================================================

GPT مسؤول عن جودة القرار التنفيذي الذي يقترحه.

عند نجاح المسار:

يتم تثبيت النتيجة كحالة مثبتة.

عند الفشل:

يتم تحليل الفشل وتصحيح المسار.

لا يتم إخفاء الخطأ.

ولا يتم تحميل المستخدم مسؤولية قرار تقني اتخذه GPT.

==================================================
25. قاعدة Milestone
==================================================

يعتبر المكون مكتملًا مرحليًا عندما:

[ ] Contract واضح
[ ] Result واضح
[ ] Engine يعمل
[ ] الاختبارات الخاصة به تمر
[ ] لا يلوث Domain State
[ ] لا يكسر downstream contracts
[ ] التكامل الأساسي مثبت
[ ] الحالة موثقة

بعد ذلك:

MILESTONE COMPLETE

ثم الانتقال إلى المكون التالي.

==================================================
26. قاعدة عدم الرجوع للخلف
==================================================

لا يعود المشروع إلى مرحلة سابقة لمجرد أن وثيقة قديمة تشير إليها.

يتم الرجوع فقط إذا ظهرت:

- Regression.
- Contract violation.
- Architectural conflict.
- Failed integration.
- Evidence جديد يثبت أن القرار السابق خاطئ.

==================================================
27. قاعدة الاستمرارية
==================================================

عند بدء محادثة جديدة:

1. قراءة EXECUTION RULES.
2. قراءة CONTROL INDEX.
3. قراءة PROJECT STATE.
4. تحديد آخر Milestone مثبت.
5. مراجعة Evidence المرتبط به.
6. تحديد أول خطوة غير مكتملة.
7. متابعة التنفيذ من هناك.

لا يبدأ المشروع من الصفر.

==================================================
28. قاعدة حالات الخطوة
==================================================

كل خطوة يجب أن تنتهي بحالة واضحة واحدة:

DONE
BLOCKED
FAILED
NEEDS DECISION

لا تستخدم حالات غامضة مثل:

- تقريبًا.
- ربما.
- يبدو.
- ننتظر.

إلا إذا تم تحديد الدليل الناقص بوضوح.

==================================================
29. قاعدة البحث عند التعارض
==================================================

إذا ظهر تعارض بين:

- الكود.
- الاختبارات.
- الوثائق.
- Git history.
- الحالة الحالية.

لا يتم اختيار أحدها بالحدس.

يتم:

1. تحديد جميع الأدلة.
2. تحديد أحدث Evidence.
3. تحديد الوثيقة المالكة للقرار.
4. تحديد ما إذا كان التعارض حقيقيًا أم مجرد اختلاف تاريخي.
5. اتخاذ القرار.
6. توثيق القرار.
7. متابعة التنفيذ.
