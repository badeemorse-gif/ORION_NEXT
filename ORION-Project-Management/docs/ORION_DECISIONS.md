==================================================
2. قاعدة تسجيل القرار
==================================================

لا يجب تسجيل كل تغيير برمجي صغير هنا.

يتم تسجيل القرار عندما يكون له تأثير:

- معماري.
- تنظيمي.
- تشغيلي.
- طويل المدى.

أمثلة:

- إنشاء طبقة جديدة.
- نقل مسؤولية من طبقة إلى أخرى.

- تغيير طريقة حقن الاعتماديات.
- تغيير طريقة التخزين.
- تغيير مصدر البيانات.
- اعتماد نمط تصميم رئيسي.
- تغيير تدفق Pipeline.
- تغيير مسؤولية Engine.
- إزالة مكون معماري.
- إضافة مكون معماري.
- تغيير بنية المستودع.
- تغيير طريقة المزامنة.
- تغيير طريقة إدارة الوثائق.

==================================================
4. حالات القرار
==================================================

PROPOSED
مقترح ولم يعتمد بعد.

ACCEPTED
تم اعتماد القرار.

REJECTED
تم رفض القرار.

SUPERSEDED
تم استبداله بقرار أحدث.

DEPRECATED
لم يعد القرار مناسبًا للتطبيق الحالي.

وجود جميع المسؤوليات داخل طبقة أو مجموعة ملفات غير منظمة

- Bootstrap
- Configuration
- Core
- Engines
- GUI
- Models
- Providers
- Reports
- Repositories
- Scheduler
- Services
- Storage
- Tests

### السبب

فصل المسؤوليات وإدارة الاعتماديات وتطوير المكونات
بصورة مستقلة نسبيًا.

### التأثير

يجب الحفاظ على حدود الطبقات ما لم يتم اتخاذ قرار
معماري جديد.

2026-08-08

- اعتماد القرارات الفنية.
- الحفاظ على الاتساق المعماري.

- التطبيق المحلي.
- تشغيل الأوامر.
- الاختبارات المحلية.
- تنفيذ Git.
- تنفيذ المزامنة.

وجود جهة فنية واحدة مسؤولة عن الاتساق والقرار.

### السياق

### المشكلة

2. يتم تحديد الوثيقة المناسبة.
3. يتم نقل أو تسجيل المعلومة فيها.
4. يتم الحفاظ على الاتساق بين الوثائق.

### السبب

منع فقدان أي معلومة بسبب موقعها داخل الوثائق.
