# ORION — سجل القرارات المعمارية

الإصدار: 1.0
الحالة: تأسيسي
المشروع: ORION
المستودع البرمجي: binansScanner
مستودع إدارة المشروع: ORION-Project-Management


==================================================
1. الغرض
==================================================

هذا الملف هو السجل الرسمي للقرارات المعمارية المهمة في مشروع ORION.

يتم تسجيل أي قرار يؤثر على:

- بنية المشروع.
- توزيع المسؤوليات.
- اتجاه الاعتماديات.
- تدفق البيانات.
- واجهات المكونات.
- طريقة التشغيل.
- التخزين.
- مزودي البيانات.
- محركات التحليل.
- محرك القرار.
- التقارير.
- API.
- GUI.
- الاختبارات.
- الأمان.
- خارطة الطريق.

الهدف هو منع فقدان أسباب القرارات مع مرور الوقت.


==================================================
2. قاعدة تسجيل القرار
==================================================

لا يجب تسجيل كل تغيير برمجي صغير هنا.

يتم تسجيل القرار عندما يكون له تأثير معماري أو طويل المدى.

أمثلة:

- إنشاء طبقة جديدة.
- نقل مسؤولية من طبقة إلى أخرى.
- تغيير اتجاه الاعتماديات.
- تغيير طريقة حقن الاعتماديات.
- تغيير طريقة تخزين البيانات.
- تغيير مصدر البيانات.
- اعتماد نمط تصميم رئيسي.
- تغيير تدفق Pipeline.
- تغيير مسؤولية Engine.
- إزالة مكون معماري.
- إضافة مكون معماري جديد.


==================================================
3. ترقيم القرارات
==================================================

يستخدم كل قرار رقمًا فريدًا:

ADR-001
ADR-002
ADR-003
...

ADR = Architecture Decision Record


==================================================
4. حالات القرار
==================================================

الحالات الممكنة:

PROPOSED
مقترح ولم يعتمد بعد.

ACCEPTED
تم اعتماد القرار.

REJECTED
تم رفض القرار.

SUPERSEDED
تم استبداله بقرار أحدث.

DEPRECATED
لم يعد القرار مناسبًا للتطبيق الحالي.

## ADR-XXX — عنوان القرار

التاريخ:

الحالة:

المجال:

### السياق

6. القرارات التأسيسية
==================================================


--------------------------------------------------
ADR-001 — اعتماد ORION كنظام متعدد الطبقات
--------------------------------------------------

التاريخ:

2026-08-08

الحالة:

ACCEPTED

المجال:

Architecture

### السياق

ORION مشروع متعدد المكونات يتعامل مع بيانات السوق والتحليل والقرارات والتقارير والتشغيل.

### المشكلة

وجود جميع المسؤوليات داخل طبقة أو مجموعة ملفات غير منظمة سيؤدي إلى صعوبة الصيانة والتوسع والاختبار.

### القرار

اعتماد بنية متعددة الطبقات تفصل بين:

- API
- Application
- Bootstrap
- Configuration
- Core
- Engines
- GUI
- Models
- Providers
- Reports
- Repositories
- Scheduler
- Services
- Storage
- Tests

### السبب

هذا التقسيم يسمح بفصل المسؤوليات وإدارة الاعتماديات وتطوير المكونات بصورة مستقلة نسبيًا.

### التأثير

يجب أن تحافظ التعديلات المستقبلية على حدود الطبقات ما لم يتم اتخاذ قرار معماري جديد.

### التبعات

قد يؤدي الفصل إلى زيادة عدد الملفات والمكونات، لكنه يوفر وضوحًا أعلى وقابلية توسع أفضل.

### الحالة

ACCEPTED


--------------------------------------------------
ADR-002 — عزل Binance عن منطق النظام الداخلي
--------------------------------------------------

التاريخ:

2026-08-08

الحالة:

ACCEPTED

المجال:

Providers

### السياق

يعتمد ORION حاليًا على Binance كمصدر رئيسي لبيانات السوق.

### المشكلة

ربط محركات التحليل مباشرة بتفاصيل Binance سيجعل تغيير مزود البيانات أو اختبار النظام أكثر صعوبة.

### القرار

استخدام طبقة Providers لعزل الاتصال الخارجي.

التقسيم الحالي يتضمن:

- Binance Client
- Binance Mapper
- Binance Provider
- Market Data Provider

### السبب

الفصل بين الاتصال الخارجي والمنطق الداخلي.

### التأثير

لا ينبغي أن تعتمد Engines مباشرة على تفاصيل Binance الخاصة بالاتصال أو الاستجابة الخارجية.

### التبعات

إضافة طبقة عزل إضافية، لكنها تزيد قابلية الاختبار والتوسع.

### الحالة

ACCEPTED


--------------------------------------------------
ADR-003 — فصل التخزين عن منطق الأعمال
--------------------------------------------------

التاريخ:

2026-08-08

الحالة:

ACCEPTED

المجال:

Storage

### السياق

ORION يحتاج إلى تخزين واسترجاع بيانات السوق.

### المشكلة

ربط منطق الأعمال مباشرة بقاعدة بيانات محددة سيجعل تغيير طريقة التخزين صعبًا.

### القرار

اعتماد طبقة Storage منفصلة عن منطق الأعمال، مع وجود Repository لتنظيم الوصول إلى البيانات.

### السبب

السماح بتغيير تقنية التخزين أو إضافة تنفيذ جديد دون إعادة بناء منطق الأعمال.

### التأثير

تتعامل الطبقات العليا مع الواجهات المناسبة بدل الاعتماد المباشر على تفاصيل SQLite.

### التبعات

زيادة عدد طبقات التجريد، مقابل مرونة أعلى.

### الحالة

ACCEPTED


--------------------------------------------------
ADR-004 — فصل GUI عن منطق الأعمال
--------------------------------------------------

التاريخ:

2026-08-08

الحالة:

ACCEPTED

المجال:

GUI

### السياق

يحتوي ORION على طبقة GUI.

### المشكلة

وضع منطق الأعمال داخل واجهة المستخدم يؤدي إلى صعوبة الاختبار وإعادة الاستخدام والصيانة.

### القرار

GUI مسؤولة عن العرض والتفاعل مع المستخدم، بينما يبقى منطق الأعمال في الطبقات المختصة.

### السبب

الحفاظ على استقلال منطق النظام عن واجهة المستخدم.

### التأثير

يجب أن تتعامل GUI مع النظام من خلال الخدمات أو طبقات التطبيق المناسبة.

### التبعات

قد تحتاج بعض العمليات إلى طبقات تنسيق إضافية.

### الحالة

ACCEPTED


--------------------------------------------------
ADR-005 — فصل API عن منطق الأعمال
--------------------------------------------------

التاريخ:

2026-08-08

الحالة:

ACCEPTED

المجال:

API

### السياق

يحتوي ORION على طبقة API.

### المشكلة

وضع منطق الأعمال داخل API سيؤدي إلى ازدواجية المنطق وصعوبة استخدامه من GUI أو Scheduler أو التشغيل الداخلي.

### القرار

API مسؤولة عن استقبال الطلبات وتوجيهها إلى طبقات النظام المناسبة.

### السبب

الحفاظ على منطق الأعمال في مكان واحد.

### التأثير

لا تتم إضافة منطق أعمال رئيسي إلى Router أو Server لمجرد سهولة التنفيذ.

### التبعات

قد تحتاج الطلبات إلى المرور بعدة طبقات قبل الوصول إلى المحرك المطلوب.

### الحالة

ACCEPTED


--------------------------------------------------
ADR-006 — اعتماد التوثيق كجزء من دورة التطوير
--------------------------------------------------

التاريخ:

2026-08-08

الحالة:

ACCEPTED

المجال:

Project Governance

### السياق

ORION مشروع طويل الأجل ويحتوي على عدد كبير من الملفات والطبقات.

### المشكلة

الاعتماد على الذاكرة وحدها يؤدي إلى فقدان أسباب القرارات وصعوبة استكمال المشروع بعد فترات طويلة.

### القرار

التوثيق جزء من دورة التطوير وليس خطوة اختيارية في النهاية.

### القاعدة

بعد كل قرار معماري مهم:

1. اتخاذ القرار.
2. تنفيذه عند الحاجة.
3. مراجعته.
4. تسجيله في الوثيقة المناسبة.

### السبب

الحفاظ على استمرارية المشروع ومنع الانحراف المعماري.

### التأثير

أي قرار مهم يجب أن يكون قابلًا للتتبع.

### الحالة

ACCEPTED


--------------------------------------------------
ADR-007 — اعتماد GPT كصاحب القرار الفني النهائي
--------------------------------------------------

التاريخ:

2026-08-08

الحالة:

ACCEPTED

المجال:

Project Governance

### السياق

يتكون فريق العمل من:

1. GPT.
2. Gemini.
3. مالك المشروع / المنفذ.

### القرار

GPT هو قائد الفريق وصاحب القرار الفني النهائي في:

- سير المشروع.
- مراجعة المعمارية.
- مراجعة الملفات.
- اعتماد التعديلات.
- إضافة التعديلات المطلوبة.
- مراجعة التفاصيل.
- تحديد الانتقال بين المراحل.

Gemini هو مهندس التنفيذ البرمجي، وينفذ التعديلات أو الأكواد بناءً على تعليمات GPT.

مالك المشروع هو المنفذ العملي للتعليمات داخل بيئة العمل المحلية، ويقوم بعمليات النسخ والحفظ والتشغيل وGit وفق التعليمات.

### السبب

تحديد واضح للصلاحيات ومنع تضارب القرارات.

### التأثير

لا يتم اعتماد قرار معماري نهائي من Gemini أو من التنفيذ المحلي وحده.

### الحالة

ACCEPTED


==================================================
7. قاعدة عدم التخمين
==================================================

عند وجود تعارض بين:

- الوثائق.
- الكود الفعلي.
- الاختبارات.
- المعلومات المتاحة.

لا يتم التخمين.

يجب تحديد الحالة الفعلية أولًا، ثم اتخاذ القرار المناسب.

إذا كان الأمر يحتاج قرارًا معماريًا، يتم تسجيله هنا.


==================================================
8. قاعدة تأثير التعديل
==================================================

قبل تعديل أي ملف يجب تقييم تأثير التعديل على:

- الملفات التي يستوردها.
- الملفات التي تستورده.
- النماذج المرتبطة.
- الخدمات المرتبطة.
- الاختبارات.
- تدفق البيانات.
- المعمارية.

لا يتم تعديل ملف بمعزل عن النظام.


==================================================
9. قاعدة الاعتماد
==================================================

لا يعتبر التعديل معتمدًا لمجرد أنه:

- تم كتابته.
- تم حفظه.
- تم تشغيله.

يجب أن يمر التعديل المناسب عبر:

تنفيذ
↓
اختبار
↓
مراجعة
↓
اعتماد


==================================================
10. القرارات المستقبلية
==================================================

أي قرار جديد يجب إضافته أسفل هذا القسم باستخدام الرقم التالي.

مثال:

ADR-008
ADR-009
ADR-010

ولا يتم إعادة استخدام رقم قرار سابق.
